# Printing — ledger, capability profile, reprint (warn, never block), operations (plan-052 M1+M2, #1166)

> **The state after M1 + M2.** There is still only **one** real transport:
> `ws_lan` (workstation dispatch, exactly as today). M1 adds NO new print path —
> it adds a **ledger**, a **printer capability profile**, a **setup wizard**, and
> a **reprint trail for money documents** (§8 — a warning, NOT a block).
> M2 adds the **observability and operations** side: a reconcile command, the
> Print jobs page API, a job-aging report and alerts.
> The workstation's offline-first print path does not change by a single line of
> behaviour.

## 1. Why a ledger exists

Before M1, Cloud was **blind** to printing. A kitchen ticket that never came out
because the printer ran out of paper at 19:40 on a Saturday was known only to
whoever was standing next to it; HQ had no way to know which shop, which printer,
or how often. The `print_jobs` ledger is where that truth is recorded.

The ledger is **not** a Cloud queue. It is a **journal**.

## 2. §1b — who owns the queue

**The operational queue (retry, dispatch, ordering) lives in the LAYER CLOSEST TO
THE PRINTER. Cloud only synchronizes the fact of "printed or not".**

| transport | Who holds the queue | Ledger mode |
|---|---|---|
| `ws_lan` | **The workstation** — a local queue that retries and dispatches itself | **journal mode**: a row is an immutable FACT, arriving later, carrying the real print time. Cloud **never** changes its status |
| `epos_http` / `webprnt` (M3) | The on-site operator | Cloud holds the job plus its payload and records the ACK |
| `cloudprnt` (M4) | **Cloud** — the printer polls Cloud directly, so Cloud IS the closest layer | Full queue mode |

This is **enforced in code**, not by convention:

- `App\Models\PrintJob::booted()` **throws** if anything `update()`s or
  `delete()`s a `ws_lan` row.
- In Go: the `internal/printjob` package **may not** import `net/http` or
  `internal/service` — an arch test (`journal_arch_test.go`) blocks it.
- A second arch test scans the `handler` package: no Cloud call may sit **after** a
  `Print()` in the same block.

The reason: if Cloud is down, the shop **must still print**. If writing the ledger
could block or slow down printing, a Cloud incident would become a printing
incident — precisely the disaster the workstation exists to prevent (RISKS PR2).

## 3. The ws_lan flow (M1)

```
The POS presses print
   → the workstation renders, connects, and prints  ← no Cloud call, no waiting
   → writes the LOCAL journal (sqlite print_jobs, with a client-generated id)
   → the sync engine drains a batch → POST /api/v1/workstation/print-jobs
   → Cloud INSERTs into print_jobs (it never UPDATEs)
```

- **The print time is the real time** (P-07): `printed_at` is the shop PC's clock
  at the moment the paper came out, stored as RFC3339 UTC. After an evening with
  no network, the sync next morning still carries the correct 20:15 from the day
  before — using the sync time would push the whole evening into the next business
  day (#1091).
- **Idempotent at the DB constraint** (P-09): `id` is generated by the workstation
  and is the PRIMARY KEY on both sides. A replay hits the PK rather than an
  application-level "does it exist" check (which two concurrent retries can slip
  past).
- Cloud returns `{accepted, duplicates}`. **A duplicate is SUCCESS** — the truth is
  already recorded — so both lists are stamped with `synced_at`. Treating a
  duplicate as an error is exactly how a retry loop becomes infinite.

## 4. Retry matrix and TTL (`config/print_jobs.php`)

Applied **only in the layer that owns the queue**.

| kind | auto-retry | attempts | TTL |
|---|---|---|---|
| `kitchen`, `bar` | ✅ | 4 | 15 minutes |
| `label` | ✅ | 3 | 1 hour |
| `report` | ✅ | 2 | 2 hours |
| `diagnostic` | ✅ | 3 | 10 minutes |
| **`receipt`** | ❌ **never** | 1 | 24 hours |
| **`red_invoice`** | ❌ **never** | 1 | 24 hours |
| **`debt_slip`** | ❌ **never** | 1 | 24 hours |
| An unknown kind (not declared) | ❌ | 1 | 15 minutes |

Two reasons, both drawn from what actually happens in a shop:

- **Money documents never auto-retry.** A lost ACK is a state in which "printed"
  and "not printed" are *indistinguishable* from a distance. A machine reprinting
  by itself means two originals of one インボイス invoice exist. A person decides,
  and the second copy carries 「Print #N」 so that even a wrong decision cannot
  produce two identical originals.
- **A kitchen ticket's TTL is 15 minutes.** A ticket from the previous shift is not
  a *late* ticket, it is a *wrong* one: the food is cold and the table has gone
  home.

Each cell is pinned by `tests/Feature/Printing/PrintRetryMatrixTest.php`.

## 5. `confidence` — never pretend to know it printed (P-33 [HARD])

A cheap ESC/POS printer on a plain TCP socket knows exactly **one** thing: that
the bytes were written. It does not know the paper ran out mid-page.

| `error_detect.level` | Printer | `confidence` |
|---|---|---|
| `none` (A) | Plain ESC/POS over TCP | `sent_only` |
| `status_back` (B) | Has ASB / DLE EOT | `confirmed` |
| `protocol` (C) | ePOS / WebPRNT / CloudPRNT | `confirmed` |

**Mapping `sent_only` → `confirmed` is absolutely forbidden.** Enforced in two
places:

- at journal intake: if the printer's profile says level A, a `confirmed` claim is
  **clamped down** to `sent_only` right at the boundary;
- on the model: an `update()` changing `sent_only` → `confirmed` **throws**.

There is no escape hatch for this rule.

## 6. The capability profile (`printers.model_profile`) — DESIGN §3b

A profile describes **what the printer can do**, never **what the slip says**. The
slip's content is ONE template for the whole fleet; the profile only selects the
**output path**.

```jsonc
{
  "preset": "escpos_generic",            // inherit, then override individual fields
  "transports": ["ws_lan"],
  "charset":  { "kanji": false, "codepages": ["CP437"] },
  "text_mode": "auto",                   // auto | native | raster
  "finishing": {
    "cut":         { "mode": "gs_v_full", "feed_before_cut": 4, "auto_cut_per_job": false },
    "drawer_kick": { "supported": false, "pin": 2, "on_ms": 120, "off_ms": 240 },
    "buzzer":      { "supported": false }
  },
  "error_detect": { "level": "none", "asb": false, "dle_eot": false },
  "health":       { "method": "tcp_dial", "interval_s": 60, "offline_after_misses": 3 },
  "columns": { "58mm": 32, "80mm": 48 },
  "quirks": []
}
```

The available presets: `escpos_generic`, `epson_tm_i`, `star_mcprint`
(`backend/config/printer_profiles.php` ↔ `internal/printer/profile.go`).

Operating principles:

- **NULL, empty and malformed are all valid** → fall back to `escpos_generic`
  (P-29). A printer nobody has described still prints; refusing to print because a
  form is missing is wrong.
- **Partial beats empty** (P-40): a field the profile declares wins, and the rest
  keep their defaults. A wizard run abandoned halfway still teaches the system a
  few correct things.
- **An unknown enum → the safest value.** An unrecognized `cut.mode` → `none` (do
  NOT send a blind command); an unknown `health.method` → `tcp_dial`.
- **Changing a profile mid-shift** (P-31) applies to the **next** print; a job
  already rendered keeps its bytes.
- Profiles sync DOWN with `GET /api/v1/workstation/printers`, so the workstation
  still renders correctly when Cloud is unreachable.

### Known quirks

| Quirk | Symptom | What to declare |
|---|---|---|
| No kanji ROM | 漢字 comes out as boxes or garbage | ⚠️ **There is no fix yet — see below.** `charset.kanji=false` → `text_mode=auto` classifies blocks (P-30) but does **not** rasterise them |
| The printer has no cutter | It does not cut | `cut.mode="none"`: feed to compensate and stop, and **send no blind cut command** (cheap firmware prints an unknown command as garbage onto the next customer's slip — P-36) |
| The cut eats the last line | The head-to-blade distance varies | Increase `feed_before_cut` |
| The drawer does not open | Different pin/timing | `drawer_kick.pin/on_ms/off_ms`, or `supported=false` → the **UI must hide the open-drawer button** and warn on a cash tender (P-37) |
| The TCP link drops on back-to-back prints | The second job fails | `quirks:["reconnect_between_jobs"]` |

> ⚠️ **"No kanji ROM" has NO escape hatch today — this row used to promise one
> (corrected #2061).** It read *"raster for the blocks that need it, numbers and
> money stay native"*, which an operator configuring a romaji-only printer reads
> as "declare it and the system copes". It does not.
>
> What `text_mode` actually does: `TextModeFor` **labels** each block `native` or
> `raster`, and the renderer records that label on the segment
> (`PrintRenderSegment.Mode`). The segment still carries **the same native
> Shift_JIS bytes** — nothing converts them to a bitmap. `RasterSegments()`
> exists and has **no caller anywhere** in either repo; the one real use of
> `Encoder.Raster()` is the **logo** block, which prints a bitmap that was
> rasterised *upstream* (an uploaded image), not glyphs.
>
> So a printer declaring `kanji=false` receives raw Shift_JIS and prints the same
> boxes. §11 of this file has always said so (*"the rasterizer has no glyphs
> yet"*) — but §11 is release-scope notes and this table is what the person
> standing at the printer reads. Both now say the same thing.
>
> Real options until a glyph rasteriser ships (#1171 Phase 2 — needs an embedded
> CJK font **and** pixel parity with the PHP renderer): use a printer with a
> kanji ROM, or run that shop in a locale whose text the ROM does cover.

## 7. The printer setup wizard (T1.4d)

`POST /api/devices/{id}/diagnostic` replaces the old three-line test button (the
quick-test button `POST /api/devices/{id}/test` **stays** — "is the printer
plugged in" is still worth a button).

The diagnostic sheet is printed so that **the person standing at the printer** can
answer:

| Block | The question | → profile |
|---|---|---|
| A | Do 漢字 / カナ / Vietnamese diacritics come out correctly? | `charset.kanji`, `text_mode` |
| B | The 32 / 42 / 48 column rulers — which line fits the paper exactly? | `columns` |
| C | Does it cut? Does it lose the last line? | `cut.mode`, `feed_before_cut` |
| D | Does the cash drawer open? | `drawer_kick.supported` |

The answers are posted to `POST /api/devices/{id}/profile`. **Every field is a
pointer**: "not answered" differs from "answered no" — merging the two means that
every skipped question overwrites a correct setting with a default.

The diagnostic sheet **goes through the ledger** with `kind=diagnostic` (P-41): it
is retryable, has a short TTL, **does not consume a 「Print #N」 number**, and does
not pollute the invoice audit trail.

## 8. Reprint — WARN, NEVER BLOCK (§4, owner ruling 2026-07-28, #1166)

> **The overriding principle: the system NEVER blocks a print command.**
> The staff member is at the counter and the customer is waiting; if the paper
> genuinely just jammed and the software refuses to reprint, the software is
> breaking the business — a larger loss than any risk it meant to prevent. The
> **old 422 has been removed**; this is the rewrite.

### 8.1 The old (wrong) behaviour vs the CORRECT one

| | Old | CORRECT (since #1166) |
|---|---|---|
| A non-manager reprints a money document with no reason | **422, blocked** | **Print it**, show a warning, record it in the ledger |
| Who may reprint | Gated by role | **Anyone**; role only changes the *level* of the warning |
| What prevents two originals | (supposedly) the 422 | **The 「PRINT #N」 mark on the paper** |

### 8.2 The endpoint

```
POST /api/v1/pos/print-jobs/reprint-advice          ← the new name
POST /api/v1/pos/print-jobs/reprint-authorization   ← the old alias, same controller
```

The two are **identical** and both return **200**. The alias is kept so older
pos-web builds do not break; the name `authorization` misstates what it does, so
new code should not use it.

Body: `{ kind, reprint_no, reprint_reason?, actor_user_id?, payment_id?, print_job_id? }`

The response:

```jsonc
{ "data": {
  "allowed": true,                  // ALWAYS true — no input can make it false
  "authorized": true,               // the old key, kept for older pos-web
  "gated": true,                    // == requires_reason_prompt (the old key)
  "requires_reason_prompt": true,   // the POS shows a reason dialog
  "marker_will_print": true,        // this slip will carry the 「PRINT #N」 mark
  "warned_without_reason": true,    // this is how it will be recorded in the ledger
  "actor_is_manager": false,
  "warnings": [
    { "code": "reprint_reason_missing",     "severity": "warning" },
    { "code": "reprint_marker_will_print",  "severity": "info" }
  ]
} }
```

**For pos-web (mandatory):** show the dialog when `requires_reason_prompt = true`
and list the `warnings` — but the **"Print anyway" button MUST ALWAYS be
available**, even with the reason field empty, and even if this endpoint errors or
times out. Skipping the dialog is a **supported** outcome, not a bug. `severity`
only picks the colour and tone (`warning` for a cashier, `notice` for a manager);
it never disables the button.

### 8.3 The three MANDATORY trails that compensate

| # | Trail | Where |
|---|---|---|
| 1 | **COUNT** — `reprint_no` | `AppendPrintHistory` (workstation) → the `print_jobs.reprint_no` column |
| 2 | **WHO PRINTED** — actor plus channel, on **EVERY print including the first** | The `print_jobs.requested_by_id` and `requested_via` columns; with no reason, `reprint_reason = NULL` and the row **derives** `warned_without_reason = true` |
| 3 | **THE MARK ON PAPER** — copy N ≥ 2 carries 「PRINT #N」 | The `reprint_marker` block, **locked** (plan-053) |

**The mark on paper is what actually prevents two originals**, not the 422. Two
slips never look like two originals.

This applies to **all four money documents**: `receipt`, `red_invoice`,
`vat_invoice`, `debt_slip`. Before #1166, `receipt` and `red_invoice` **declared**
the `reprint_marker` block but **printed nothing** — a reprinted receipt was
indistinguishable from the original. That was the very hole the 422 was believed to
be covering.

The **first copy carries NO mark** — if the original were marked too, the mark
would mean nothing.

**Nobody can turn it off:** `reprint_marker` is `type: locked`. Publishing a
template that disables, deletes, edits the wording of, or reorders this block is
rejected by `TemplateValidator` (`LOCKED_BLOCK_MODIFIED` /
`LOCKED_BLOCK_REORDERED`) — pinned by
`tests/Feature/Printing/ReprintMarkerLockTest.php`, plus a byte-level test on the
Go side in `workstation/internal/service/print_reprint_marker_test.go`.

### 8.4 What did NOT change

**Auto-retry on money documents is still FORBIDDEN (PR1).** A machine deciding to
print another copy is entirely different from a person deliberately pressing
reprint: the person's name is in the ledger and the paper carries a mark, whereas a
machine re-firing an ACK-lost receipt is the path to two originals nobody knows
about. An expired money-document job moves to `needs_attention` for a person to
decide; it never prints itself.

**P-11: reprinting while the original is still `delivering` IS allowed.** The
person standing at the printer, looking at a slip jammed halfway out, knows better
than any status column. The advisor does not ask about the previous job's status —
it looks only at the *document kind* and the *copy number*.

**P-12: the number is taken from the ledger itself, never from the printer path.**
`print_jobs` both *issues* and *records* it (see 8.6 — `AppendPrintHistory` is gone). The atomic `BEGIN IMMEDIATE`
mechanism is unchanged. The workstation takes the number **BEFORE** the paper moves
(a failed print still consumes a number) — because the slip must carry `#N` at the
moment it prints, and because counting afterwards would let the counter be reset by
unplugging the printer.

**Kitchen tickets are not gated:** `kitchen` / `bar` / `label` / `report` /
`diagnostic` are never asked for a reason, no matter which copy — holding a kitchen
ticket back to collect a written reason is operationally absurd, and no money is
involved. They still land in the ledger in full (trails #1 and #2).

### 8.5 What happens when the network is down?

The advisor lives in Cloud while the print path is offline-first, so with no
network the workstation **still prints**, still counts, and still stamps
「PRINT #N」 (the mark lives in the local formatter and does not depend on Cloud).
The journal row arriving later carries the `reprint_reason` the staff member typed
on the spot.

`warned_without_reason` is a **DERIVED value**, not a stored column:
`PrintJob::warnedWithoutReason()` computes it from (the kind is a money document) ×
(`reprint_no ≥ 2`) × (the reason is empty) — the same function
(`ReprintAdvisor::warnedWithoutReason`) that the warning endpoint uses. Why it is
not stored: every input already sits on that same row, so a stored copy could only
**drift** from the columns beside it, and history from before the ruling would need
a backfill. Because it is derived, a shop offline all evening — or an older
workstation build that has never heard of the concept — still reaches Cloud with
the correct trail, with no device update needed.

The field appears in the Print jobs page API (`PrintJobResource`) alongside
`reprint_marker_printed`. The M2 reconcile report
(`journal_money_reprint_no_reason`) lists money-document reprints with no reason for
a manager to review.

**An unknown actor must not spoil the whole batch.** `requested_by_id` is a foreign
key and a journal batch is ONE insert — a stale or wrong id from a tablet
remembering a deleted user would drop an entire evening of printing, and those rows
exist nowhere else. So intake looks the user up first: an unknown id is lowered to
NULL, the print is still recorded, and only the person's name is unknown.

### 8.6 Where the copy number comes from — PER KIND, PER SCOPE (#1875)

`N` used to come from `payments.metadata.print_history`: **one counter shared by
`receipt` + `red_invoice` + `debt_slip` on a payment**. So printing a receipt made
that customer's *first* red invoice come out stamped 「BAN IN #2」 — the mark
claiming "this is a copy" about an original. `AppendPrintHistory` is gone; the
existing `print_history` JSON stays on disk as history and nothing reads it.

The counter now lives in **`print_jobs` itself**, which already carried `kind`,
`order_id` and `payment_id` — and, decisively, already held every money document
printed since #1166, so the new counter continues the real history rather than
restarting at 1. No new table, no new column, no backfill.

Cơ chế `Reserve` → print → `Confirm`, bốn thuộc tính load-bearing của nó, và
thang quyết định **scope** ba nhánh (payer được `payment_id` chỉ tên → thanh toán
non-split duy nhất của đơn → cả **order family** `linkedOrderIDs`) là chuyện NỘI
BỘ workstation — `internal/printjob/reserve.go` và `handler/resolvePrintScope`.
**Đọc bản chính ở [`workstation/CLAUDE.md`](../../workstation/CLAUDE.md)**, mục
"The copy number is PER KIND and PER SCOPE". Trang này cố ý không chép lại: hai
bản mô tả cùng một cơ chế sẽ trôi khỏi nhau (#2336 — ruling: docs của app viết
chính ở app đó, nơi khác chỉ ref).

`lastConfirmedPaymentID` đã bị xoá cùng thay đổi này: một hoá đơn đỏ không chỉ
đích danh payer từng mượn thanh toán của **khách cuối** để đếm, khiến hoá đơn đỏ
đầu tiên của chính khách đó in ra như bản sao.

**Auto-printed receipts now journal too.** They previously called the printer
directly with a hard-coded `1` and wrote **no ledger row at all** — the most
common sheet a shop produces was the one the ledger could not see, and it
consumed no number, so the cashier's next "In biên lai" also printed an unmarked
#1 and the customer held two sheets each claiming to be the original. With no
printer configured nothing is journalled (the print is a no-op; a row would be a
lie).

### 8.7 Asking what has already been printed

`GET /api/lan/print/status?order_id=` (workstation, LAN) returns a per-kind tally:

```jsonc
"red_invoice": {
  "printed": true,
  "order_scope": { "count": 1, "last_printed_at": "…", "last_status": "printed" },
  "by_payment": [ { "payment_id": "…", "count": 2, "last_printed_at": "…" } ]
}
```

`count` is the highest number **issued**, so the next sheet is `count + 1`. Served
from local SQLite, so it stays correct with the internet down — which is why the
flag is derived rather than stored. **There is no stored flag**: a boolean on
`orders` cannot say WHICH guest already has paper, and a second copy of that truth
drifts from the ledger.

Cloud side: `GET /api/v1/shops/{shop}/print-jobs?order_id=&payment_id=` filters the
ledger the same way (applied *after* the org + branch scoping, so naming another
shop's order narrows to nothing rather than reaching it).

A field being **absent** means "this workstation is older than #1875 and cannot
tell you" — never "nothing was printed". Rendering a confident "chưa in" from a
missing field is how a second original ends up in a customer's hand.

## 9. Registry deduplication (T1.5, P-18)

Printers used to be registrable in **two** unrelated places: the `printers` table
and `peripheral_devices`. Two ledgers for one machine means a shop configures the
same printer twice with two addresses, and neither screen sees the other's row.

- `receipt_printer` / `kitchen_printer` / `bar_printer` have been **removed from**
  `PeripheralDeviceService::ALLOWED_TYPES`. The API returns 422.
- `printers` is the **only door** for printers; 周辺機器 now means payment devices
  (payment_terminal, coin_changer) plus POS/workstation/kiosk.
- Migration `2026_07_28_170002` **warns and STOPS** if any printer rows remain — it
  does **not delete silently**. If a shop really did configure something there,
  that configuration exists nowhere else and deleting it would lose it.

The ops command (the only permitted escape route):

```sh
# Lệnh `peripheral-devices:purge-printers` ĐÃ GỠ ở #2507 — production còn 0
# hàng thuộc `RETIRED_PRINTER_TYPES`. Bất biến P-18 (không đường nào của
# plan-052 xoá hàng peripheral device) vẫn được ghim ở `RegistryDedupTest`.
```

## 10. Operations (M2)

### 10.1 `print-jobs:reconcile` — the reconcile command

```sh
php artisan print-jobs:reconcile                       # scan everything and send alerts
php artisan print-jobs:reconcile --dry-run             # preview; NO writes, NO alerts
php artisan print-jobs:reconcile --branch=<branch-id>  # one branch
php artisan print-jobs:reconcile --transport=cloudprnt # one transport
php artisan print-jobs:reconcile --no-alerts           # reconcile quietly
```

The scheduler runs it **every 15 minutes** (`printing.print-jobs.reconcile`) —
exactly the shortest TTL in the matrix (kitchen tickets, 15 minutes): any sparser
and a dead ticket sits unnoticed for a whole shift.

**What the command may do, per the queue-ownership rule (§1b):**

| transport | What the command may do |
|---|---|
| `ws_lan` | **READ ONLY.** Count, detect, print a report. It never changes a single column — pinned by a test that snapshots whole rows before and after |
| `cloudprnt` (and epos/webprnt in M3) | Apply the TTL table: past its TTL → `expired`; `delivering` stuck past the threshold → `needs_attention` |

**There is no retry path in this command**, for any kind. An expired money document
is NOT silently `expired`; it moves to `needs_attention` for a person to decide
(PR1) — somebody may be waiting for that invoice.

**What it detects on the ws_lan side** (report only):

| Code | Meaning | What to do |
|---|---|---|
| `journal_needs_attention` | An ACK-lost job waiting for a person | Print jobs page → resolve |
| `journal_stale_delivering` | `delivering` for longer than `stale_delivering_seconds` | Check the printer on site |
| `journal_past_ttl_open` | Past its TTL but not terminal | The workstation decides, not Cloud |
| `journal_late_sync` | The journal arrived later than `late_journal_seconds` | **The uplink is broken, NOT the printer** |
| `journal_money_reprint_no_reason` | A money document was reprinted offline with no reason | For a manager to review (exactly the promise in §8) |

The thresholds live in `config/print_jobs.php` → `reconcile.*`. The command is
**idempotent**: running it twice in a row changes no column (not even
`updated_at`).

Heartbeat: `printing.reconcile.last_run_at` (cache). A key that is hours old means
the scheduler is dead — and a dead scheduler looks exactly like a shop with no
incidents.

### 10.2 Reading `status` and `confidence`

| status | Meaning | Who handles it |
|---|---|---|
| `queued` | Recorded, not yet sent | The layer owning the queue |
| `delivering` | Being sent | — |
| `printed` | Sent successfully **(check confidence!)** | — |
| `failed` | The printer reported a clear error | A person |
| `needs_attention` | **Sent, but nobody confirmed** (ACK lost) | **A person** |
| `expired` | Past its TTL, will not print | — |

`confidence` comes with a `confidence_label` so the UI does not have to derive one:

- `printed_confirmed` — the printer (or the protocol) confirmed the paper came out.
- `printed_sent_only` — **all that is known is that the bytes left**. A cheap
  ESC/POS printer on a plain socket does not know the paper ran out mid-page.
  **These must not be displayed identically.**

### 10.3 The `needs_attention` procedure

1. Open the Print jobs page
   (`GET /api/v1/shops/{shop}/print-jobs?status=needs_attention`).
2. Look at the `kind`. Kitchen/bar/label → the workstation retries per the matrix;
   usually all that is needed is to check the paper.
3. **Money documents** (receipt / red_invoice / debt_slip): the system **never
   reprints them automatically**. Two routes:
   - the paper is needed → **reprint deliberately** (call
     `POST /api/v1/pos/print-jobs/reprint-advice` for the warning — it is **never
     refused**, §8 — then print: it consumes a 「PRINT #N」 number, stamps the mark
     on the paper, and records the actor plus the reason in the ledger);
   - the paper was obtained another way, or is no longer needed → **resolve**:
     `POST /api/v1/shops/{shop}/print-jobs/{job}/resolve`
     with `resolution` = `printed_by_hand` | `discarded` and a **mandatory**
     `reason`.

`resolve` is a **manager permission** (cashiers can view but not resolve) and is
written into its own `print_job_resolutions` table (append-only, UNIQUE per job) —
it **never touches the ledger row**, because a `ws_lan` row is the workstation's
immutable fact (§1b). A second call returns the first decision (200, idempotent); a
job already `printed` returns 409 — the books say it printed, so there is nothing
to "resolve".

**`resolve` is NOT a reprint button** and cannot become one: the enum has only two
values, and `reprint` is not among them.

### 10.4 Alerts (T2.3)

Sent through the notification platform to the branch's `shop-manager`:

| Alert | Trigger | Debounce |
|---|---|---|
| `print.printer_silent` | A printer has been silent past the threshold | **Per PRINTER** — three dead printers = three alerts, one each |
| `print.jobs_need_attention` | The `needs_attention` backlog reaches the threshold | Per branch |
| `print.money_document_failed` | At least one money document is `failed`/`needs_attention` and unresolved within the window | Per branch |

The thresholds and windows live in `config/print_jobs.php` → `alerts.*` (nothing is
hard-coded). Two properties of the debounce:

1. while the fault persists, **one alert per window** (`Cache::add`, atomic — two
   workers on the same tick still produce one alert);
2. **the cooldown is released as soon as the fault clears**. A printer that dies, is
   fixed, and dies again the same evening is NEW news, not a repeat.

**A silent printer is INFERRED, never probed** (P-38): `ws_lan` infers it from a
silent journal (`printers.last_seen_at` stops moving), and `cloudprnt` infers it
from the printer no longer polling — the printer sits behind the shop's NAT and
Cloud cannot dial back. A printer **never seen at all** (`last_seen_at` is null) is
NOT treated as silent: a newly installed printer is not a broken one, and that kind
of false alert is the fastest way to make a shop mute the notification channel.

If a profile declares a health cadence slower than the shared threshold
(`interval_s × offline_after_misses`), **the longer one wins** — a printer
configured to be slow is not a late printer.

### 10.5 Where to look quickly

| Question | Command / place to look |
|---|---|
| Journal not yet uploaded to Cloud | `printjob.Journal.PendingCount()` — a number climbing for days means **the uplink is broken**, NOT printing |
| Printer state | `printers.last_status` — the UPOS enum: `ok / cover_open / paper_end / paper_near_end / offline / error` |
| Jobs needing a person | `print_jobs.status = needs_attention` → `print-jobs:reconcile` plus the Print jobs page |
| The age of the backlog | `meta.aging` in `GET /shops/{shop}/print-jobs` — bucketed by **duration** (`<1d / 1-2d / 2-7d / 7d+`), so it reads the same in Tokyo and Hanoi (#1091) |

The Print jobs page's `from`/`to` filters, by contrast, **are** timezone-aware:
they are the branch's BUSINESS day, applied to the **real print time**
(`COALESCE(printed_reported_at, created_at)`), not the sync time — otherwise an
evening without a network would fall entirely into the next day.

**Deploy order: backend FIRST, workstation SECOND.** An old workstation with a new
Cloud runs normally (it simply has no journal); a new workstation against an old
Cloud gets a 404 on the journal endpoint and its queue backs up — no data is lost,
but do not do it in that order.

## 11. What is NOT in M1/M2

- No new transport (`epos_http` / `webprnt` / `cloudprnt`) — they are hard-blocked
  by #1171 Phase 2 (Cloud must be able to render the payload itself; today the 13
  templates are Go code inside the workstation, and a cloud-only shop has no Go
  process to render with). See DESIGN §3c.
- **The rasterizer has no glyphs yet**: `text_mode`/`TextModeFor` already choose the
  right output path per block and `escpos.Finishing` exists, but *building a bitmap
  from a font* is not done — it needs an embedded CJK font **and** must match the
  PHP renderer pixel for pixel (DESIGN §3c), so it belongs to #1171 Phase 2 rather
  than being a standalone Go task.
- **No UI yet**: M2 finished the API, the command and the alerts; the admin Print
  jobs screen belongs to `web/admin/`.
- **No per-attempt history table**: `print_jobs.attempts` is a NUMBER, not a list.
  For `ws_lan` the attempts happen on the workstation — the layer owning the queue —
  and it reports up the count plus the last error. The detail API says exactly that
  much (`delivery.attempts` / `max_attempts` / `auto_retry_allowed` /
  `queue_owner`) rather than inventing a history Cloud does not have.

## 13. Cờ `print_template_renderer_enabled` — mặc định BẬT (#1945)

Điều kiện chặn cứng ở mục 11 ("Cloud phải tự render được payload") đang được gỡ

### Kiểm mà không cần máy in nhiệt

Dựng một `cmd/ws-server` scratch (`WS_APP_CONFIG_DIR` riêng — **đừng** dùng
`~/.ws-app`, nó có thể đang trỏ production), đăng ký máy in với
`connection_type: "network"` (không phải `"tcp"`) trỏ `127.0.0.1:9100`, rồi cho
một socket listener ghi lại byte. In hai lượt quanh thay đổi cần đo và so:

```
cờ TẮT: seam log scope=system version=0 · print_jobs.template_version = system:0
cờ BẬT: seam log scope=shop   version=1 · print_jobs.template_version = shop:1
```

Byte đầu tiên lệch chỉ đúng chỗ đổi; đuôi decode `shift_jis` là chữ trên giấy.

**Giới hạn phải nói ra:** đây là byte gửi tới **cổng máy in**, không phải tờ
giấy. Nó không phủ nhiệt/độ đậm, dao cắt, codepage ROM của máy thật, hay tràn
khổ 58mm. plan-053 **T4.4 vẫn cần ảnh giấy thật** và phép đo này không đóng
được nó.

⚠️ **P-39 (plan-052) KHÔNG canh chỗ này.** P-39 từ chối transport
`epos_http`/`webprnt`/`cloudprnt` ở **tầng cấu hình**; đây là thứ workstation
render trên `ws_lan`.

**Không fail-closed**, kể cả `red_invoice`: plan-052 §4 / #1166 là ruling đang có
hiệu lực — không endpoint in nào được từ chối in; cái nó nợ là **một dấu vết**.
Và sau #2062 thì `red_invoice` không phải hoá đơn GTGT. Chứng từ thuế thật lấy số
từ `info.TaxBreakdown` đóng băng lúc phát hành, chưa từng đi qua code này.

**Không in thêm dòng cảnh báo lên giấy**: một dòng phát ra tạo nghĩa vụ
byte-parity Go↔PHP trên ca mà fixture chung không phủ — đẻ ra đúng loại phân kỳ
im lặng đang đóng.

### Bài học về cổng

**Không ô golden nào đổi khi sửa lỗi này.** Đơn golden luôn mang `TotalAmount`
dương và rate trên mọi dòng, nên ma trận 126 ô **chưa bao giờ chạm** hai nhánh ấy.
TR-40, byte-parity, golden — không cổng nào bắt được. Một fixture "đơn đẹp" che
đúng những nhánh chỉ chạy khi dữ liệu thiếu.

## Print image originals live on a NAMED disk (#2136)

`PrintImageStore` keeps the uploaded bytes of a print image (brand logo, tier
background) on the disk named by **`filesystems.print_images`**
(`PRINT_IMAGES_DISK`, default `local`). It is deliberately **not**
`filesystems.default`, and deliberately **not** the public upload disk that
`filesystems.uploads` points at.

### Why private is correct here

These bytes never reach a client. What a workstation pulls is the rastered
bitmap, base64-encoded in `print_image_rasters.data`; nothing in `backend/app`
builds a URL from `original_path`. The originals are re-read server-side only,
when `rasterFor()` needs a width that was not pre-rendered. So private storage is
the correct posture — do not "fix" this to match the public upload disk.

### Why it must be named rather than inherited

`print_image_assets` has **no `disk` column**. While the store rode
`filesystems.default`, the location of the bytes was not a property of the row at
all — it was whatever the environment variable happened to be when they were
written. Flipping `FILESYSTEM_DISK` therefore orphaned every original.

The blast radius is narrow but silent: the two printable widths (384 / 576) are
pre-rastered into the database, so receipts keep printing. What disappears is
`rasterFor()` for any *other* width — a template declaring an odd width simply
loses its image block, with no error and no log, because TR-05 makes a missing
original a silent `null`.

TR-05 says a **deleted** image must not stop printing. It does not say a
**misconfigured disk** should stay quiet. Those two shared one code path, and
that is the defect #2136 fixed.

### Reading legacy bytes, and the warning

The read path tries the configured disk first, then the plausible legacy ones
(`filesystems.default`, `public`, `local`). Finding bytes on a legacy disk still
serves them — no data is dropped — but emits a `warning` naming both disks. A
genuinely deleted image stays silent, so the warning keeps meaning something.

### Moving the bytes

```sh
# Lệnh `print-images:migrate-disk` ĐÃ GỠ ở #2507 — production còn 0 hàng
# `print_image_assets`, nên bản vá một lần đó hết đối tượng. Nếu sau này lại
# cần dời disk: sao chép nguyên bản sang disk mới (KHÔNG xoá nguồn) rồi ghi lại
# đường dẫn; git history giữ bản cũ.
```

It **copies, never deletes**. Reclaiming the old copies is a separate, deliberate
step once the move has been verified.
