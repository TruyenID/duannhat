# Interfaces Reference

This document lists every interface that is part of, or directly consumes, the TempoFast system. New features must declare which interfaces they touch so that planning, testing, and documentation stay in sync.

## Surfaces

| Name | Type | Stack | Path / Repo | Dev URL | Status |
| ---- | ---- | ----- | ----------- | ------- | ------ |
| Web app | Web SPA | Next.js 16 (App Router), React 19, Tailwind 4, shadcn/ui | `frontend/` (in this repo) | `http://localhost:5430` (docker compose) | Active |
| REST API | HTTP API | Laravel 13, Sanctum 4, l5-swagger | `` (in this repo) | `http://localhost:5400` (docker compose) | Active |
| Mobile app | Mobile | Not chosen yet | — | — | Planned |

> **Note:** This repo is a monorepo. `frontend/` and `` live side by side and share `schemas/`, `.omnify/`, and `docs/`. There is no separate admin panel — admin and end-user views are both inside the Next.js web app and gated by role.

## Web app

The Next.js web app is the **only** end-user interface today. It is split into two URL trees:

| Tree | Pages | Purpose |
| ---- | ----- | ------- |
| `/brands/[brandSlug]/...` | products, product types, categories, materials, recipes, menus | Brand-scoped catalog management |
| `/shops/[shopSlug]/...` | warehouses, stock, transfers, counts, alerts, disposals, production, zones, tables, menu | Shop-scoped inventory operations and per-shop menu management (availability + price overrides on HQ-cloned menus) |

Authentication is delegated to the upstream console portal — see [Console portal](#console-portal) and [SSO Authentication](../guide/sso-authentication.md). The frontend never holds passwords.

Type definitions for backend models are generated by Omnify into `web/admin/src/types/models/base/`. Hand-written extensions live in `web/admin/src/types/models/`. See [`web/admin/AGENTS.md`](../../../web/admin/AGENTS.md).

## REST API

The Laravel backend exposes a versioned REST API under `/api/v1`. All controllers live in `app/Http/Controllers/Api/V1/` and are grouped by domain:

| Group | Path prefix | Controllers |
| ----- | ----------- | ----------- |
| Product | `/api/v1/hq/{brandSlug}/...` | Product, ProductType, ProductOption, ProductOptionValue, ProductSku, Category, Material, Recipe, Menu, VariantUnit |
| Inventory | `/api/v1/shops/{shopSlug}/...` | Warehouse, StockLevel, StockTransaction, StockTransfer, StockCount, StockAlert, Disposal |
| Shop | `/api/v1/shops/{shopSlug}/...` | Zone, Table, Menu (read + item availability/price overrides) |
| Production | `/api/v1/shops/{shopSlug}/...` | MaterialBatch, ProductionOrder |
| System | `/api/v1/...` | File, Locale, UserContext |

Swagger UI is generated from controller annotations by `darkaonline/l5-swagger`. See [API Overview](api-overview.md) for response shape, error codes, and pagination conventions, and [Swagger Rules](../contributing/swagger.md) for annotation rules.

## Console portal

The DXS console portal (external project) is the identity provider and the source of truth for organizations, brands, branches, users, and roles. TempoFast never creates these entities locally — it caches them via SSO sync.

| Property | Value |
| -------- | ----- |
| Role | Identity provider, organization registry |
| Auth flow | OAuth2/OIDC BFF (handled by `dxs/laravel-auth`) |
| Sync target | `Brand`, `Branch`, `Organization`, `User`, `Role` tables in this app |

> **Important:** Local test users **cannot** be created by `php artisan db:seed` alone. The local dev workflow is: log in via the console portal once → users/brands/branches sync down → then run `LocalDevSeeder` for sample products. See [Test Users](test-users.md).

## Mobile app

A mobile app is planned but does not exist yet. No stack chosen, no repo, no API contract reserved. When work starts:

1. Add a row to the [Surfaces](#surfaces) table with stack, repo path, and dev URL.
2. Decide whether it consumes the existing `/api/v1` namespace or needs a dedicated `/api/mobile` namespace.
3. Register the OAuth2 client in the console portal.

## Adding a new interface

When introducing any new surface (mobile, partner portal, Slack bot, CLI, webhook receiver, …):

1. Update the [Surfaces](#surfaces) table — never add a parallel doc.
2. Document its auth model. Workforce surfaces reuse Platform SSO via `dxs/laravel-auth`; a fundamentally new auth path requires an [Authorization](../explanation/authorization.md) update.
3. If it ships with new pages or routes, link them from this doc.
4. Note any dev URL or local path so future agents can run it without guessing.
