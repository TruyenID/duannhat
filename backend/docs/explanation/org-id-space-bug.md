# Authorization Bug — Organization ID Space Mismatch

> ⚠️ **READ THIS BEFORE TOUCHING ANY POLICY OR REFACTORING `ChecksShopContext` / `ResolvesOrganization`.** This is a landmine that has bitten the codebase once and will bite again if the underlying ID-space distinction is not preserved. Tests can lie about it.

**Hotfix date**: 2026-04-14
**Severity**: Critical (every shop/HQ endpoint silently returned 403 against real seed data)
**Affected files**: 4 (1 trait + 3 policies)
**Broken authorization branches**: ~12

---

## TL;DR

Several `*Policy` classes were comparing the user's **SSO shadow id** with a model's **local Organization PK** — two columns that sit in different UUID spaces and only ever match by accident in the unit test harness. In production (and against any real seeder data), the comparison is always false, so every protected endpoint returns 403, including for the org admin who logged in.

The fix routes every comparison through either:

- the model's `organization` BelongsTo relation (compare shadow vs shadow), or
- the [`ResolvesOrganization`](../../app/Policies/Traits/ResolvesOrganization.php) helper trait (resolve user shadow → local id, then compare local vs local).

Do **not** simplify either of these back to a direct `$user->console_organization_id === $model->organization_id` even though it looks cleaner — that's the broken pattern.

---

## Symptom

Frontend console (admin-web shop dashboard, inventory dashboard, etc.):

```
GET  /api/v1/shops/<slug>/menus/<uuid>           → 403 Forbidden
GET  /api/v1/shops/<slug>/menus/<uuid>/products  → 403 Forbidden
GET  /api/v1/hq/<brand>/inventory/stock-levels   → 403 Forbidden
POST /api/v1/hq/<brand>/.../variant-units        → 403 Forbidden
```

Logged-in user is the org admin (`admin@famgia.com / password`) — should have access to everything in the org. Backend logs show the request **was authenticated** (Sanctum token resolved a valid User), it just failed authorization at the policy layer.

Unit tests for the same endpoints pass.

---

## Background — Two ID spaces

The project is built to integrate with an external SSO IdP (DXS console). Almost every tenant entity (User, Organization, Brand, Branch) carries **two parallel ids**:

```
┌─────────────────────────────────────────────────────────────────────┐
│  organizations table                                                │
│                                                                      │
│  id                       UUID  ← LOCAL primary key                 │
│                                  Auto-generated by `HasUuids` when  │
│                                  the row is INSERTed locally. All   │
│                                  other tenant tables FK at this id. │
│                                                                      │
│  console_organization_id  UUID  ← SHADOW id from SSO                │
│                                  Issued by the external IdP. Mirror │
│                                  copy. We do not control the value. │
└─────────────────────────────────────────────────────────────────────┘
```

| Column | Source | Example |
|---|---|---|
| `users.console_organization_id` | Mirrored from SSO IdP at login | `00000000-aaaa-4aaa-aaaa-000000000001` |
| `organizations.id` (LOCAL PK) | Auto-generated UUID v7 by `HasUuids` | `019d8a35-fb5b-7254-b8af-3cfaa0d27795` |
| `organizations.console_organization_id` | Mirrored from SSO IdP, equal to user's | `00000000-aaaa-4aaa-aaaa-000000000001` |
| `menus.organization_id` | LOCAL FK to `organizations.id` | `019d8a35-fb5b-7254-b8af-3cfaa0d27795` |
| `warehouses.organization_id` | LOCAL FK | `019d8a35-fb5b-...` |
| `products.organization_id` | LOCAL FK | `019d8a35-fb5b-...` |

→ **`users.console_organization_id` and `{tenant_table}.organization_id` are NEVER equal** outside of unit tests. They live in different ID spaces.

Why two? Because the SSO IdP owns the shadow id (it's stable across our `migrate:fresh`), but tenant tables need a local FK target inside our own DB. The two id spaces accidentally coincide only in `tests/Pest.php`, which forcibly aligns them for factory simplicity.

## The broken pattern

```php
// ❌ BAD — what every affected file did
return $user->console_organization_id === $model->organization_id;
//     ↑ shadow id from SSO            ↑ LOCAL FK to organizations.id
//     2 different UUID spaces — almost always FALSE → AuthorizationException → 403
```

### Trace with real data

```
$user->console_organization_id  = "00000000-aaaa-4aaa-aaaa-000000000001"  (SHADOW)
$menu->organization_id          = "019d8a35-fb5b-7254-b8af-3cfaa0d27795"  (LOCAL PK)

"00000000..." === "019d8a35..." → FALSE
                                → policy returns false
                                → $this->authorize() throws AuthorizationException
                                → Laravel renders HTTP 403
```

## Why tests passed while production was broken

[`tests/Pest.php`](../../tests/Pest.php) sets up the test Organization with both columns equal:

```php
Organization::factory()->create([
    'id'                       => '00000000-0000-0000-0000-000000000001',  // ← forced
    'console_organization_id'  => '00000000-0000-0000-0000-000000000001',  // ← matches id
    ...
]);
```

In the test universe, `organizations.id === organizations.console_organization_id`, so `users.console_organization_id === menus.organization_id` is also true (both = `"0000...0001"`). The broken policy returns true → tests pass.

But `MockDataSeeder` (used for `migrate:fresh --seed`) does NOT force the alignment:

```php
Organization::firstOrCreate(
    ['console_organization_id' => self::ORG_CONSOLE_ID],  // only sets shadow id
    [
        'name' => 'Famgia',
        // ← does NOT set 'id' explicitly
    ]
);
```

→ `id` is auto-generated as a fresh random UUID → never equals the shadow id.
→ Same code that passes tests immediately 403s every request.

In **production** the SSO IdP issues `console_organization_id` independently, so the local PK and the shadow id will likewise never align by accident.

**Lesson:** Test data does not reflect production data. A passing test suite with no integration smoke against real seeders is no protection.

## The fix pattern

There are two correct approaches depending on what helper your policy already uses.

### Pattern A — Compare via the `organization` relation

Use this when the policy doesn't yet use a helper trait (or for one-off comparisons in code that doesn't fit the trait shape):

```php
// ✅ GOOD — go via the organization relation
return $model->organization?->console_organization_id === $user->console_organization_id;
```

This joins `organizations` table to get the shadow id, then compares shadow vs shadow. **Requirement**: the model must expose an `organization()` BelongsTo relation pointing to `App\Models\Organization`. This is what `MenuPolicy::belongsToUserOrganization()` and the HQ Product/ProductSku/ProductOption policies already do.

### Pattern B — Use the `ResolvesOrganization` trait

Use this in policies where you have a reusable helper to lean on:

```php
class StockLevelPolicy
{
    use ResolvesOrganization;

    public function view(User $user, StockLevel $stockLevel): bool
    {
        $stockLevel->loadMissing('warehouse');

        return $stockLevel->warehouse !== null
            && $this->belongsToUserOrg($user, $stockLevel->warehouse);
    }
}
```

`belongsToUserOrg()` internally:

1. Reads `$user->console_organization_id`
2. Looks up the LOCAL Organization id where `console_organization_id` matches (cached per-request)
3. Compares that local id against `$model->organization_id` (also local) — **same space, correct**

The trait is at [`app/Policies/Traits/ResolvesOrganization.php`](../../app/Policies/Traits/ResolvesOrganization.php).

### What NOT to write

```php
// ❌ NEVER write this even if it looks "simpler"
return $user->console_organization_id === $model->organization_id;
```

This is the bug. It will 403 every request against real data. The fact that it might pass a unit test means nothing.

## Production cutover checklist

Run through this before shipping any policy or auth code to a real environment.

1. **Verify SSO populates `users.console_organization_id`** with a real shadow id from the IdP on every login. Print it from middleware once during smoke testing. If it's null, **every** policy returns false → 403.

2. **Verify every shop-scoped tenant table populates `organization_id` with the LOCAL Organization PK**, not the shadow id. The model's `organization()` relation must resolve. Tables in scope today:
   - `menus`, `zones`, `tables` (shop-side)
   - `products`, `product_skus`, `variant_units` (HQ-side)
   - `warehouses`, `stock_levels`, `stock_transactions`, `disposal_records` (inventory)
   - Any new domain table you add later that needs tenant scoping

3. **Do NOT "simplify"** any policy back to a direct `$user->console_organization_id === $model->organization_id` comparison. The block comments in [`ChecksShopContext.php`](../../app/Policies/Traits/ChecksShopContext.php) and this doc both warn about it. Treat that line as a code-review red flag.

4. **Add an integration smoke test** that hits at least one endpoint per affected module **after running `MockDataSeeder` (not factory data)**. The gap that let this bug land in the first place is the absence of any test that uses real seeder output. Suggested smoke list:
   - `GET /api/v1/shops/{shop}/menus/{menu}` against seeded shop + branch menu
   - `GET /api/v1/shops/{shop}/stock-levels` against seeded warehouse
   - `GET /api/v1/hq/{brand}/products/{product}/skus/{sku}/units` against seeded product

5. **If you ever decide to drop the local PK** (e.g. make `organizations.id` equal to `console_organization_id` permanently): update policies + seeders + SSO sync layer + every tenant FK in **one migration**. Partial migration reintroduces the 403.

## How to detect future occurrences

### Grep checklist

When reviewing a new policy, search for these patterns inside the policy body:

```bash
# Direct shadow vs LOCAL pk comparison — the broken pattern
grep -rn "console_organization_id === .*organization_id" backend/app/Policies
grep -rn "organization_id === .*console_organization_id" backend/app/Policies
```

If those return any line **without** the words `->organization?->` between them, that line is broken.

### Pest architecture test (suggested, not yet added)

A Pest 4 `arch()` test could enforce the rule at CI time:

```php
arch('policies must not compare shadow id directly against organization_id')
    ->expect('App\Policies')
    ->not->toUse('console_organization_id === ')
    ->ignoring(['App\Policies\Traits\ChecksShopContext']);
```

(This is a sketch — Pest's `arch()` API is not strong enough for raw string matching, would need a custom expectation. Worth adding once the test suite has time.)

### Code-review heuristic

Any PR that touches a policy and contains a literal `$user->console_organization_id` should be reviewed for which side of the `===` comparison it sits on. If the right side is `$model->organization_id` directly, the PR is wrong — comment with a link to this doc.

## Why this happened

Three contributing factors:

1. **Test data is not production data.** [`tests/Pest.php`](../../tests/Pest.php) force-aligns the two ID spaces for factory convenience. Anyone reading the test setup naturally assumes "the policy works because the test passes". It doesn't.

2. **Copy-paste bug propagation.** All 3 affected policies (`VariantUnitPolicy`, `StockLevelPolicy`, `DisposalRecordPolicy`) **already imported the correct helper** (`use ResolvesOrganization;`) but then ignored it and wrote the broken direct comparison anyway. Most likely they were copy-pasted from an earlier broken policy without the author noticing the trait was sitting right there waiting to be used.

3. **No integration smoke test against real seeder data.** Every test in the suite uses `factory()->create()` which inherits the test's force-aligned org. Nothing exercises the policy against a row whose `organization_id` is a fresh random UUID, the way `MockDataSeeder` actually creates them.

The first one is structural and the hardest to fix — see the production checklist for the integration-smoke recommendation.
