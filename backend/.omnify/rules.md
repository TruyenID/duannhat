# Omnify Architecture Rules (CRITICAL)

## Single Source of Truth

The YAML schema files in `./schemas/` are the **single source of truth** for the database schema.
All migrations, models, requests, resources, and TypeScript types are generated from these schemas.

## Workflow

1. Edit schema YAML files in `./schemas/`
2. Run `omnify validate` to check for errors
3. Run `omnify generate` to generate migrations + codegen

## NEVER Do These

- **NEVER** create or edit migration files directly — edit the schema YAML, then run `omnify generate`
- **NEVER** edit auto-generated files (they get overwritten on next generate)
- **NEVER** edit `schemas.json`, `.omnify/lock.json`, or `.omnify/versions/` — managed by omnify
- **NEVER** manually write SQL DDL (CREATE TABLE, ALTER TABLE) — omnify handles this
- **NEVER** manually write Policy PHP files — define `policies` in schema YAML, omnify generates them

## How To

- **Add a column**: Add a property in the schema YAML → `omnify generate`
- **Add a relation**: Add an Association property in the schema YAML → `omnify generate`
- **Add an enum**: Create a new YAML file with `kind: enum` → reference it with `type: EnumRef`
- **Add a table**: Create a new YAML schema file → `omnify generate`
- **Rename a column**: Change the property name in YAML → `omnify generate --force`
- **Add an index**: Add to `options.indexes` in the schema YAML
- **Add a policy**: Add `policies` block to the schema YAML → `omnify generate` (generates Laravel Policy classes)

### Service generation defaults (#81, v3.23.0+)

Every project `kind: object` schema gets a generated base service **by default**
(no `options.service` block required). Skipped automatically:

- `options.service: false` (explicit opt-out)
- `kind: pivot` / `enum` / `partial` / `extend`
- Names ending in `Translation` (Astrotomic sidecars)
- `options.hidden: true`
- Package-owned schemas

Property-level flags drive service behaviour:

- `searchable: true` → `?search=foo` full-text search
- `filterable: true` → `?field=value` WHERE filter
- `sortable: true` → sort whitelist entry
- `lookupable: true` → `lookup()` projection column
- `defaultSort: asc|desc` → default ORDER BY (at most one property per schema)

When asked to add a service, DO NOT re-introduce the legacy
`options.service.searchable[]` / `.filterable[]` / `.defaultSort` /
`.lookupFields[]` / `.eagerLoad[]` / `.eagerCount[]` block-level keys.
Those are deprecated and will be removed in a future major version. Always
migrate to property-level flags. Eager loads live in the editable sibling
service via `applyListEagerLoads()` / `applyFindByIdEagerLoads()` /
`applyLookupEagerLoads()` overrides — never in YAML.

### `*ServiceBase.php` contract (hardened #75–#79, v3.21.0+)

Every generated base service enforces security + correctness guarantees that
the AI assistant must NOT regress when editing consumer code. When asked to
modify a service, check the inline `#75.2` / `#75.3` / `#75.7` / `#75.8` /
`#76` / `#77` / `#78` / `#79` markers before touching the surrounding block:

- Sort column is whitelisted — never pass raw user input to `orderBy()` (#75.2).
- `created_by_id` / `updated_by_id` are forced from `Auth::id()`; client
  values are `unset()` first. Never re-introduce `?? Auth::id()` fallbacks (#75.3).
- `forceDelete()` / `emptyTrash()` cascade translations explicitly — do not
  replace with query-builder shortcuts that skip the sidecar (#75.7).
- `lookup()` has a hard row cap (500) — never remove it (#75.8).
- `findById($id, bool $withTrashed = false)` and `lookup(['with_trashed' =>
  true])` are the ONLY correct way to touch soft-deleted rows via the base
  (#79). Do not regenerate consumer code with plain `Product::withTrashed()->
  findOrFail($id)` workarounds.
- Translatable `lookup()` / `list()`-sort use LEFT JOIN + COALESCE on the
  sidecar (#76). Consumers MUST NOT replace this with a plain `select(['name'])`
  which reads the mirror column instead of the locale translation.
- Translatable writes compose on Astrotomic's native `fill()` + the
  generator-emitted `flushTranslations()` helper (#78 Step 3, v3.21.0+). Only
  flat `attr:locale` input keys are accepted — the old `translations` wrapper
  was removed in v3.21.0 and is NOT supported. When migrating consumer seeders,
  flatten `['translations' => ['ja' => ['name' => ...]]]` to `['name:ja' => ...]`.
- Strict `@param array{...}` shapes list every schema field by name with
  typed values. Do not downgrade to `array<string, mixed>` (#77).

## Consumer-mode Data Files (frontend / standalone TS projects)

When `omnify-ts` is invoked from a consumer project that points its `omnify.yaml`
at a remote `schemas.json` (HTTP URL or npm package), the following files are
maintained at the consumer project root:

- `.omnify/input.lock.json` — **Commit this**. Pins the sha256 of the upstream `schemas.json` for reproducible CI builds. Auto-updated by `omnify-ts`; refuse-to-overwrite by `omnify-ts --frozen-lockfile`.
- `.omnify/cache/schemas.json` — Local cache of the most recently fetched remote `schemas.json`. May be gitignored or committed depending on team preference.

These files are **not** managed by the Go binary — they belong to the consumer
side. The backend's `lock.json` (above) and the consumer's `input.lock.json`
have different semantics and never collide.

## Editable Extension Files
These files are generated **once** and are safe to customize:
- `app/Models/*.php` — Your custom model extensions (extends base model)
- `app/Http/Controllers/Api/V1/**/*Controller.php` — Your custom controllers (extends base)
- `app/Services/**/*Service.php` — Your custom services (extends base)
- `app/Http/Requests/*Request.php` — Your custom request extensions
- `app/Http/Resources/*Resource.php` — Your custom resource extensions
- `app/Policies/Omnify/{Name}Policy.php` — Your custom policy extensions
- `database/factories/*Factory.php` — Your custom factory extensions

# Schema Design Guide

## Schema Kinds

| Kind | Purpose | Key Fields |
|------|---------|------------|
| `object` (default) | Database table with columns | properties, options, associations |
| `enum` | Enum type (no table) | values (simple list or with labels) |
| `pivot` | Join table for ManyToMany | pivotFor: [Model1, Model2], properties |
| `extend` / `partial` | Add fields to existing schema (generates Model + Factory only, no Requests/Resources) | target, properties, priority |

## Property Types

### String Types
| Type | Description | Key Fields |
|------|-------------|------------|
| String | VARCHAR | length (default: 255) |
| Text | TEXT | - |
| MediumText | MEDIUMTEXT | - |
| LongText | LONGTEXT | - |
| Email | VARCHAR, validated as email | length |
| Password | VARCHAR, hidden | length |
| Uuid | UUID/CHAR(36) | - |

### Numeric Types
| Type | Description | Key Fields |
|------|-------------|------------|
| TinyInt | TINYINT | unsigned |
| Int | INT | unsigned |
| BigInt | BIGINT | unsigned |
| Float | FLOAT | - |
| Decimal | DECIMAL | precision, scale, unsigned |
| Boolean | BOOLEAN | - |

### Date/Time Types
| Type | Description | Key Fields |
|------|-------------|------------|
| Date | DATE | - |
| Time | TIME | - |
| DateTime | DATETIME | useCurrent, useCurrentOnUpdate |
| Timestamp | TIMESTAMP | useCurrent, useCurrentOnUpdate |

### Other Types
| Type | Description | Key Fields |
|------|-------------|------------|
| Json | JSON column | - |
| File | Polymorphic file attachment | multiple, maxFiles, accept, maxSize, collection |
| Point | Spatial POINT | - |
| Coordinates | Lat/Lng pair (JSON) | - |
| Enum | Inline enum | enum: [val1, val2] |
| EnumRef | Reference to enum schema | enum: SchemaName |
| Association | Relationship | relation, target |

### Common Property Fields
- `displayName`: LocalizedString — display name (plain string or locale map `{ja: 名前, en: Name}`)
- `description`: LocalizedString — detailed description (tooltips, help text)
- `placeholder`: LocalizedString — input placeholder text
- `nullable`: Allow NULL (default: false)
- `default`: Default value
- `unique`: Unique constraint
- `hidden`: Hide from API responses
- `fillable`: Allow mass assignment (default: true)
- `searchable`: Include in full-text search (?search=keyword). Used by CRUD API generation
- `filterable`: Allow filtering (?field=value or ?field_min=N&field_max=N)
- `sortable`: Allow sorting (?sort=field or ?sort=-field)
- `translatable`: Enable multi-language translation via Astrotomic/laravel-translatable. Generates a `{model}_translations` table + Translation model. Only allowed on: String, Text, MediumText, LongText, Email, EnumRef, Json
- `rules`: Validation rules — generates both Laravel validation and Zod schemas

### LocalizedString Type
Used by `displayName`, `description`, `placeholder` (on properties), and `label` (on enum values):
```yaml
# Plain string
displayName: Title

# Locale map
displayName:
  ja: タイトル
  en: Title
```

## Associations (Relationships)

| Relation | Creates Column? | Example Use |
|----------|----------------|-------------|
| ManyToOne | Yes (`{name}_id` FK) | Post belongs to User |
| OneToMany | No | User has many Posts |
| OneToOne | Yes (FK + unique) | User has one Profile |
| ManyToMany | No (uses pivot) | Post has many Tags |
| MorphTo | Yes (`{name}_type` + `{name}_id`) | Comment belongs to commentable |
| MorphOne | No | Post has one Image |
| MorphMany | No | Post has many Comments |
| MorphToMany | No (uses morph pivot) | Post has many Tags (polymorphic) |
| MorphedByMany | No (inverse of MorphToMany) | Tag morphed by many Posts |

**Not supported** (dev-managed): `HasOneThrough`, `HasManyThrough` — no DB changes needed, add manually to editable model.

### Association Example
```yaml
author:
  type: Association
  relation: ManyToOne
  target: User
  onDelete: CASCADE    # CASCADE, SET NULL, RESTRICT, NO ACTION
```

### Reverse relations are auto-generated (v3.9.0+)
Declare `ManyToOne` / `OneToOne` on the child only — the parent base model
gets the matching `HasMany` / `HasOne` accessor automatically. Method name
is the camelCase pluralized child schema name (e.g. `ProductOption` →
`productOptions(): HasMany`). Declare `OneToMany` explicitly only when you
need a custom name, `orderBy`, or to override the inferred behavior.

### orderBy on a relation (v3.9.0+)
Add a default sort to `OneToMany` / `ManyToMany` / `MorphMany` /
`MorphToMany`. Single column shorthand or list of `{column, direction}`:

```yaml
options:
  type: Association
  relation: OneToMany
  target: ProductOption
  mappedBy: product
  orderBy: position           # shorthand: ascending by position

units:
  type: Association
  relation: OneToMany
  target: VariantUnit
  mappedBy: productSku
  orderBy:
    - column: is_base
      direction: desc
    - column: position
```

The referenced column must exist on the target schema (validated at
generate time). `orderBy` is **only** for collection relations — it's an
error on `ManyToOne` / `OneToOne` / `MorphTo`. The column itself is **not**
auto-created — declare it as a normal property on the target schema.

## Schema Options

```yaml
options:
  id: true              # true (default), false, BigInt, Int, Uuid, Ulid, String
  timestamps: true       # created_at + updated_at (default: true)
  softDelete: true       # deleted_at column
  tableName: custom_name # Override table name
  authenticatable: true  # Laravel Authenticatable trait
  indexes:
    - columns: [email]
    - columns: [status, created_at]
      type: btree        # btree, hash, fulltext, spatial, gin, gist
  unique: [email]        # Unique constraint(s)
  defaultOrder: position # v3.9.0+: global Eloquent scope sorts every query
  # or
  defaultOrder:
    - column: priority
      direction: desc
    - column: created_at
```

`defaultOrder` generates `addGlobalScope('defaultOrder', ...)` on the base
model. Bypass with `Model::withoutGlobalScope('defaultOrder')->...`. Each
column must exist on the schema.

## Policies (Cedar-style ABAC)

Define authorization policies directly in the schema YAML. Only valid on `kind: object` schemas.

```yaml
policies:
  - permit: [view, list]
    when: status = "published"
    desc: "Published posts are public"
  - permit: [view, edit, delete]
    when: author = $user
    desc: "Authors can manage their own posts"
  - permit: [create]
    desc: "Any authenticated user can create"
  - forbid: [delete]
    when: status = "published"
    desc: "Published posts cannot be deleted"
```

**Actions**: `view`, `list`, `create`, `edit`, `delete`, `*` (all)

**Evaluation order**: forbid first → permit → default deny

**Conditions**: `property = "literal"`, `property != "value"`, `property >= 1000`, `property in ["a", "b"]`, `author = $user` (ManyToOne), `$user in members` (ManyToMany), `$user in org.members` (through), `$user.role = "admin"`, `$ip in cidr(10.0.0.0/8)`, `deadline > $now`

**Multiple conditions (AND)**: Use array `when: [cond1, cond2]`

See the Policies guide topic for full syntax reference.

## Best Practices

- **Schema files**: PascalCase (`Customer.yaml`, `PostStatus.yaml`)
- **Property names**: camelCase in YAML → auto-converted to snake_case in DB
- **Groups**: Use directory structure (`./schemas/blog/Post.yaml`)
- **DisplayName**: Always provide — used for labels, docs, and UI
- **EnumRef vs Enum**: Use EnumRef for shared/localized values, inline Enum for simple schema-specific values
- **Associations**: Always set `onDelete` on ManyToOne (CASCADE or SET NULL)
- **ManyToMany**: Use `joinTable` to control pivot table name

## Consumer-side TypeScript Codegen (`omnify-ts`)

`omnify-ts` is the npm-distributed CLI that turns `schemas.json` into
TypeScript types, Zod schemas, form metadata, and payload builders. It is
auto-invoked by `omnify generate` in backend projects, and can also be
run standalone in consumer projects (frontend repos that have no Go
binary or Laravel install).

| Command | Description |
|---|---|
| `omnify-ts` | Read `omnify.yaml` in cwd and generate TypeScript output |
| `omnify-ts --config <path>` | Use a specific config file |
| `omnify-ts --input <spec> --output <dir>` | Ad-hoc explicit override (skips config). `<spec>` accepts a local path, an `http(s)://` URL, or an `@org/pkg/file` npm specifier. |
| `omnify-ts --update` | Force re-fetch the remote `schemas.json` and refresh `.omnify/input.lock.json` |
| `omnify-ts --frozen-lockfile` | CI mode: fail loudly if the remote `schemas.json` hash differs from the lockfile, or if the lockfile is missing |
| `omnify-ts --force` | Regenerate all auto-generated files (no effect on user-editable wrappers) |

The consumer-mode `omnify.yaml` accepts a top-level `input:` field that
omnify-ts sniffs to dispatch to the right resolver (local file / HTTP fetch /
Node module resolution). See the **codegen-typescript** guide topic and the
config guide's "Consumer shape" section for details.

## Workflow Slash Commands (via the omnify MCP server)

Once `omnify init` has wired up `.mcp.json` and the project is open in Claude
Code, the `omnify` MCP server exposes 8 workflow skills as slash commands.
Each one walks Claude through one phase of an Omnify Laravel feature
lifecycle: **init → plan → execute → ship**, plus debug + maintenance.

| Slash command | Phase | When to use |
|---|---|---|
| `/mcp__omnify__init` | One-time | Bootstrap the project for AI collaboration: install required packages, scaffold `docs/`, scan codebase. Run BEFORE any planning. |
| `/mcp__omnify__plan` | Plan | Plan a feature: scope → design → tests → atomic tasks. Stops at an approval gate. |
| `/mcp__omnify__execute` | Implement | Run the approved plan: feature branch, task-by-task commits, pint, code review, optional browser verify. |
| `/mcp__omnify__complete` | Ship | Generate handoff doc, sync `docs/`, push branch, open PR. Never force-pushes, never auto-merges. |
| `/mcp__omnify__debug` | Debug | Scientific debugging: symptoms → hypotheses → root cause → fix → regression test. Independent from plans. |
| `/mcp__omnify__fix_docs` | Maintenance | Audit and fix existing `docs/` against the project standard. |
| `/mcp__omnify__status` | Read-only | Show plan/debug index, active progress, suggest next command. |
| `/mcp__omnify__resume` | Read-only | Pick up where the last session stopped (reads `plans/` and `debugs/` frontmatter). |

`/mcp__omnify__status` is a Claude Code MCP slash command. The shell command is `omnify status`. `omnify:status` is not a valid terminal command.

**Codex CLI users:** `omnify init` also writes `.codex/config.toml` with an `[mcp_servers.omnify]` block. Codex doesn't use the `/mcp__omnify__*` slash syntax — the omnify tools and prompts are exposed to the model directly via MCP. The project-scoped `.codex/config.toml` only loads when the project is marked as **trusted** in Codex; otherwise copy the `[mcp_servers.omnify]` block into `~/.codex/config.toml`. The section name MUST be `mcp_servers` with an underscore — Codex silently ignores `mcp-servers` / `mcpservers`. Verify the server is connected with `codex mcp` (or check the model's tool list inside a Codex session).

**Knowledge containment:** these prompts live inside the `omnify` binary and
are delivered to Claude per-session via MCP. They are **never** written to
disk in your project — that's by design (issue #41) so the methodology
stays inside the Omnify org and out of customer repositories.

If the slash commands don't appear in Claude Code, verify the omnify MCP
server is connected with `claude mcp list`.

# Project Conventions (issue #84)

These are HARD RULES for any AI assistant working in an Omnify-based Laravel project with a React `admin-web`. They're bundled into the MCP rules tool so every Claude Code session picks them up automatically — not just those running through `omnify:plan` or `omnify:execute`.

The rules exist because they've already bitten shipped projects in production. Re-teaching them on every agent run wastes everyone's time.

## 1. Admin UI uses `@godxjp/ui` — no exceptions

Any React/TypeScript file under `admin-web/` (or equivalent admin React project) MUST use components from `@godxjp/ui` when the design system ships an equivalent. Forbidden: hand-rolled inline styles, native HTML elements like `<button>` / `<input>` / `<select>`, or local re-implementations of the library's primitives.

**Required components** (this list isn't exhaustive — check the library's index for the full set):

- Layout: `Sidebar`, `SidebarProvider`, `SidebarInset`, `Card`, `Separator`
- Inputs: `Input`, `Textarea`, `Select`, `Combobox`, `Switch`, `Checkbox`, `RadioGroup`, `DatePicker`, `Slider`
- Forms: `Form`, `FormField`, `FormItem`, `FormLabel`, `FormControl`, `FormDescription`, `FormMessage` (react-hook-form wrapped by the library)
- Feedback: `Alert`, `Badge`, `Skeleton`, `Toast`, `Dialog`, `Sheet`, `Popover`, `Tooltip`, `DropdownMenu`
- Data: `Table`, `Pagination`, `Tabs`, `Avatar`, `Accordion`, `Collapsible`
- Action: `Button` (every variant — `default`, `destructive`, `ghost`, `link`, `outline`, `secondary`)

**Setup requirements** every admin-web project needs, in this order:

1. `pnpm add @godxjp/ui tw-animate-css`
2. Wrap the root layout in `<UIProvider>` so theme tokens resolve everywhere
3. Import a reference `globals.css` with Tailwind v4 design tokens (`bg-input-background`, `h-element`, semantic `success`/`warning`/`info`/`error`). If the project has no reference, copy from a known-good sibling repo and leave a `// REVIEW: source repo` comment.

When you hit a library gap — missing component, broken prop, theme token that doesn't resolve — DO NOT silently inline-style around it. Instead:

- Run `gh issue create -R godx-jp/godx-tempo-ui` with a minimal repro snippet, OR
- Drop `bug-reports/<YYYY-MM-DD>-<slug>.md` at the repo root for later triage

Then add a `// TODO(godx-tempo-ui#NNN): remove once upstream ships X` comment on the workaround. That way the inline CSS is time-boxed instead of becoming permanent tech debt.

## 2. Translatable fields use the library's `translatable` prop

A schema property with `translatable: true` renders as ONE `@godxjp/ui` input with the built-in `translatable={{locales: ...}}` prop — NOT four stacked Cards (one per locale) with plain `<Input>` children.

**Correct:**

```tsx
<Input
  translatable={{ locales: { ja: '日本語', en: 'English', vi: 'Tiếng Việt', fil: 'Filipino' } }}
  value={translations.name}
  onChange={(v: TranslatableValue) => setField('name', v)}
/>
<Textarea
  translatable={{ locales: { ja: '日本語', en: 'English', vi: 'Tiếng Việt' } }}
  value={translations.description}
  onChange={(v: TranslatableValue) => setField('description', v)}
/>
```

**Wrong** (and the reason this rule exists):

```tsx
// NEVER do this — four stacked locale Cards is an anti-pattern
<Card><CardHeader>日本語</CardHeader><Input /></Card>
<Card><CardHeader>English</CardHeader><Input /></Card>
<Card><CardHeader>Tiếng Việt</CardHeader><Input /></Card>
<Card><CardHeader>Filipino</CardHeader><Input /></Card>
```

State shape MUST be per-field `Record<LocaleCode, string>` matching the library's `TranslatableValue` type. The backend FormRequest / service MUST accept top-level locale keys (`{ja: {...}, en: {...}}`) so the frontend payload maps 1:1 to what the backend validates.

If the existing code uses the four-Card anti-pattern, migrate it as part of any task that touches that form — don't add more of it.

## 3. Seeders go through generated services, not raw Eloquent

Any seeder that writes into an Omnify-managed table MUST call the corresponding service:

```php
// RIGHT — service dispatches fill() → flushTranslations() → DB::transaction wrap
$service->create([
    'handle' => 'ACME',
    'name'   => ['ja' => '株式会社ACME', 'en' => 'ACME Inc.'],
    // ...
]);

// WRONG — $fillable strips locale-keyed arrays before the translatable trait sees them
Brand::updateOrCreate(['handle' => 'ACME'], [
    'name' => ['ja' => '株式会社ACME', 'en' => 'ACME Inc.'],
]);
```

The wrong form silently saves the parent row (Brand) and leaves `brand_translations` empty. You won't see an error — you'll just see NULL translations at runtime weeks later.

Services wrap create/update in `DB::transaction`, route via Astrotomic's native `fill()` (which handles `attr:locale` keys), and call the generator-emitted `flushTranslations()` helper which persists sidecar rows correctly even under `WithoutModelEvents`.

Idempotent seeder pattern (`findBy(handle) ? update : create`):

```php
class DemoBrandSeeder extends Seeder {
    public function run(BrandService $service): void {
        $seeds = [
            ['handle' => 'ACME', 'name' => ['ja' => '株式会社ACME', 'en' => 'ACME Inc.']],
            // ...
        ];
        foreach ($seeds as $seed) {
            $existing = Brand::where('handle', $seed['handle'])->first();
            if ($existing) {
                $service->update($existing, $seed);
            } else {
                $service->create($seed);
            }
        }
    }
}
```

If the project's editable `*Service.php` sibling doesn't exist yet, it's auto-created on the next `omnify generate` run — one-time, never overwritten. You don't need to write it by hand. Just make sure `omnify generate` has run before the seeder tries to call it.

## 4. Schema YAML hygiene — grouping + comments

When creating or editing `.yaml` schemas:

**Group by domain subfolder.** Flat `schemas/*.yaml` doesn't scale past ~10 entities. Use:

- `schemas/catalog/` for product / brand / category / variant
- `schemas/orders/` for order / order_item / cart / checkout
- `schemas/auth/` for user / role / permission / session
- `schemas/billing/` for invoice / payment / subscription
- Match the subfolder to the project's existing domain language

**Every schema file** MUST carry a top-level block comment:

1. What this table represents in the domain
2. Who/what writes it, who/what reads it (roles, services, pages)
3. Lifecycle if the entity has one — ASCII state diagram is fine

```yaml
# Product
# -------
# Catalog item that can be listed in a storefront. Owned by a Brand.
# Written by: catalog admin (editor role) via ProductService.
# Read by:    customer-facing storefront, order pipeline, analytics.
# Lifecycle:  draft → active → archived (archived rows stay queryable
# but are hidden from customer-facing listings).
#
#   [draft] --publish--> [active] --archive--> [archived]
#     ^                     |
#     └─────unarchive───────┘

displayName: Product
kind: object
# ... properties below ...
```

**Every `properties:` entry** MUST carry an inline comment explaining intent (not just type):

```yaml
properties:
  slug:
    # URL-safe handle used in customer-facing routes. Written once at
    # create time by the editor; immutable afterwards (changing it breaks
    # inbound links). Uniqueness scoped per brand.
    type: String
    length: 100
    unique: true
  status:
    # Lifecycle state. See diagram in the header. The StatusTransition
    # policy in app/Policies/ProductPolicy.php enforces legal transitions;
    # bypass via raw SQL at your own risk.
    type: EnumRef
    enum: ProductStatusEnum
    default: draft
```

The comment answers "what is this field for, who touches it, what breaks if I change it". Schemas with 15+ fields and zero comments are unreadable after six months — you can't distinguish load-bearing from legacy.

## 5. Forms render (almost) every schema field by default

When generating an admin form from a schema, the default is to render EVERY field. If the user wants fields hidden, they'll say so afterwards — don't pre-filter.

Missing fields on a generated form force the user to either edit YAML or drop to raw SQL, which is the exact workflow Omnify exists to kill. Err on the side of showing too much; the user will trim.

Form best practices (spawn a sub-agent to research if you're unsure of the right shape for a particular screen type):

- Layout: single-column for short forms, two-column for long ones (group by section)
- Label placement: top-aligned unless the design system's `FormLabel` default says otherwise
- Field ordering: required first, then optional, then metadata (timestamps, audit)
- Error surfaces: inline under the field via `FormMessage`, plus a summary banner for catastrophic errors
- Save/Cancel: sticky footer on long forms, inline on short ones — `Button` from the library with `default` + `outline` variants
- Keyboard: Enter submits, Tab follows reading order, Escape confirms cancel if dirty
- Translatable: convention #2 above (single `<Input translatable>` per field)

## 6. Ask-then-research, delegate to Sonnet sub-agents

When planning a feature, the assistant MUST:

1. **Ask the user whether to research** before burning budget on it
2. **Delegate research to Sonnet sub-agents** when the user opts in — parallel, cheap, context-isolated from the main session
3. **Cross-reference the sub-agent outputs** in the main session to produce informed questions

The underlying principle: questions asked without context produce generic fluff ("what's your goal?", "who triggers this?") that the user has to patiently answer from scratch. Questions informed by research land on real design decisions immediately. BUT some users arrive with a spec already done — forcing them through re-research wastes everyone's time.

### The consent question (ask FIRST, before any research)

Every planning skill (`omnify:plan` Phase 0.4, `omnify:quick` Phase 0.4) MUST ask the user one question via `AskUserQuestion` at the top of the workflow, offering 3–4 concrete options:

```
a) Full research — web best practices + project docs + sibling code
   (Sonnet sub-agents in parallel, 5–10 min wall-clock)
b) Project only — skip web, read project docs + sibling code
   (2–3 min, one sub-agent or inline)
c) User has a spec — skip research, paste the spec, treat it as source of truth
   (main session still does a small project-domain load to map spec → project conventions)
d) Not sure — default to (a)
```

Do NOT skip this question, even for "obviously trivial" asks — the user might still have a spec ready. If the ask really is trivial AND the user picks (b) or (c), route them to `/mcp__omnify__quick` instead of proceeding with `omnify:plan`.

### Sub-agents with Sonnet (not the main session)

When the user opts into research, **delegate to sub-agents via the `Agent` tool** with:

- `subagent_type: general-purpose`
- `model: "sonnet"` (override)

Do NOT run `WebSearch` / `WebFetch` / bulk doc reads from the main session. Rationale:

- **Context isolation.** Web search results can be 5–10k tokens per fetch. Loading them into the main session eats the context window the planner needs for DESIGN / TESTS / TASKS later. A sub-agent returns a 200–400 word compressed summary instead.
- **Cost.** Sonnet is cheaper than Opus per token, and research is comprehension + summarization — Sonnet's sweet spot. Opus-level reasoning is for the cross-reference + question synthesis step, not the raw reading.
- **Parallelism.** Two sub-agents in one tool-use block run concurrently. Wall-clock is bounded by the slowest, not the sum.

The established shape: **2 parallel sub-agents** (web + project) in `omnify:plan`, **1 sub-agent** (web + project + sibling combined) in `omnify:quick`. Each sub-agent's prompt enforces a word cap (400 for plan, 200 for quick) and a strict output structure so the main session can consume the summary without re-reading raw sources.

### Cross-reference happens in the main session

The sub-agents gather raw material; the main session synthesizes. After both sub-agents return, compare what the web sources recommend against what the project already does. The questions you ask the user come out of the **gap** between them:

- **Bad question:** *"What's the goal of this feature?"*
- **Good question:** *"Shopify's pattern throttles stock alerts at 1/hour per SKU. Your `NotificationService` doesn't have a throttle. Do you want to add one, or fire-every-time?"*

The good question compresses 10 rounds of clarification into 1 round of decision-making. The bad one wastes everyone's time AND makes the user re-explain domain concepts the planner could have learned for free.

### Cite what the sub-agents read

Every source (URL, file path, MCP tool call result) that ends up informing a design decision gets recorded as `@see <path> — <one-sentence reason>` in `NOTES.md` → `DESIGN.md` `## Context` block. Sub-agent prompts require returning the source list verbatim; preserve it when consuming the summary.
