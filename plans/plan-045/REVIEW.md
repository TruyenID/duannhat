# Plan-045 — Code Review

**Summary: has-critical** — the money math (rounding snapshot, group-once tax, refund exact-reversal, Cloud↔Go parity) is correct and faithfully mirrored on both engines, but the **sync-UP refund endpoint on Cloud is not idempotent**, so a lost-response retry of a *partial* LAN refund double-applies (real money loss). Two other gaps break DESIGN contracts: the `conditions[]` ledger never syncs DOWN, and the tax-rounding open-shift lock (409) was never implemented. Test coverage is well below TESTS.md (no HTTP/authorization/open-shift tests).

Counts: **critical 2 · warning 6 · info 6**

## What's correct (verified)

- **Rounding primitive parity.** `RoundingMode::roundTax/roundToStep/taxStep` (PHP) and `roundToStep/taxStep/currencyStep` (Go) match: `half_up` default, `round_up`=ceil, `round_down`=floor, null decimals → currency step, byte-identical to pre-plan-045. Cloud/Go zero-decimal currency sets align.
- **Snapshot immutability.** Both engines read `order.tax_rounding_mode/decimals` (the snapshot), never the live setting — `applyPricing` (PHP:2393-2395), `computeOrderTotalsFromDB`→`orderRoundingSnapshot` (Go, reads the order row, comment explicitly forbids shop_settings). Tested by `TaxRoundingConfigTest` ("later shop-setting change does NOT re-round") + Go `TestOrderRoundingSnapshot_DrivesRecompute`.
- **Refund exact-reversal.** Refund lines excluded from group-once (`rateSubtotalsForOrder`/`stampLineTaxAmounts` skip `refund_of_item_id != null`; Go `computeOrderTotalsFromDB`/`stampLineTaxAmounts` skip via SQL `refund_of_item_id IS NULL OR = ''`). Negated snapshot folded directly via `applyRefundLines` on both sides (faithful port). Over-refund guarded (`refunded_quantity + qty ≤ quantity`, `+1e-9` tolerance PHP / integer Go), re-checked inside the tx under `lockForUpdate` (PHP) / SQLite writer-serialization (Go). Refund tax proportional + negated + once-rounded with the order snapshot.
- **Cloud↔Go pricing parity** asserted by Go `TestPriceGroups_CloudParityAcrossModesDecimals` + `TestApplyRefundLines_*` (excluded/included/orphan-rate-group).
- **`AllocateGroupTax` ≥0-clamp gap (gap #1) closed** — refund lines never enter the allocator on either side.
- **SKU-carry (gap #2)** — Go refund line copies `product_sku_id`; `TestReadOrderItemForSync_Plan045_RefundLineCarriesSKU` guards it.
- **Reconcile adopts rounding snapshot (gap #3)** — `reconcileOrderFromCloud` (sync_service.go:1574-1595) copies mode+decimals; tested.
- **Stock-out exclusion** — `OrderClosingService::deductStock` filters `whereNull('refund_of_item_id')`.
- **Ledger reconciliation** — `writeConditions` regenerates tax/discount, never touches `refund`; refund conditions append-only. `RefundOrderItemTest` asserts Σ(tax conditions)==tax_amount post-refund and the append-only refund row.
- **Migrations** clean & Omnify-generated (self-FK RESTRICT on `refund_of_item_id`, indexes on `order_conditions`; SQLite migration 040 mirrors + `repairLegacySchema`). No hand-edited generated files. `RefundException` has structured `error_code` + `render()`.
- **Sync DOWN** refund lines arrive as negative-qty items with `refund_of_item_id`/`refunded_quantity` COALESCE-upserted; rounding snapshot COALESCE-adopted; `PullBranch` mirrors the two rounding keys into `shop_settings` (tested).
